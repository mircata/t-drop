# T-Drop, Next.js port

Monthly t-shirt subscription site for Bulgaria (t-drop.net). This repo replaces the WordPress site whose backup sits in `wordpress-site/t-drop.zip`.

## Run it

```bash
npm install
cp .env.example .env.local   # then fill in DATABASE_URI and PAYLOAD_SECRET
npm run migrate              # creates the tables
npm run seed:admin           # creates admin@t-drop.local / tdrop-local-admin for /admin
npm run dev
```

Node 22 LTS and npm (`.nvmrc` pins it). No Bun. The dev server picks a free port when 3000 is busy.

Emails (password reset) print to the dev console unless `RESEND_API_KEY` is set. Registration no longer needs email verification to finish — that's turned off for now (`Customers.ts`, `auth.verify: false`); see the TODO there to turn it back on before production.

Local database: PostgreSQL 17 from Homebrew (`brew services start postgresql@17`, then `createdb tdrop`). `DATABASE_URI=postgres://localhost:5432/tdrop` works with no password. Production points the same variable at Supabase Frankfurt.

## Where things live

- `src/app/(site)/` is the public site, one folder per page. `page.tsx` is the page, `layout.tsx` holds the fonts, header and footer. Routes match the old WordPress slugs: `/`, `/about`, `/join`, `/join/delivery`, `/register`, `/your-profile`, `/checkout`, `/payment-confirmation`, `/payment-failed`. (`/cart` was WooCommerce-era filler content and was removed 2026-09-16 along with the header's cart button — this is a subscription, not a cart-based store.) The `(site)` folder name is not part of the URL.
- `src/app/(account)/` is the signed-in account area (`/account` and its sub-pages), a separate route group with its own root layout (`(account)/layout.tsx`) purely because Next.js requires one per route group — it renders the same `SiteHeader`/`SiteFooter` as the rest of the site (an earlier minimal `AccountHeader` made the header look inconsistent across the site and was removed 2026-09-16). Rebuilt to the 2026-09-15 Figma redesign, all six pages: `/account` (dashboard — a "Преден дроп" strip for the most recently delivered pick, a "Предстоящ дроп" section for the current one with size/gender shown and editable, and the design/size/gender picker for the next one, all as a single choice per `CategorySelections`), `/account/orders` (История — table with a Category column resolved by matching each payment's month against the customer's picks, and a "Преглед" button opening an order-detail popup), `/account/address` (Доставка — recipient name, phone, postcode, courier (`Customers.shipping`), `src/lib/actions/shipping.ts`), `/account/payment` (Плащане — native Stripe Elements, see below), `/account/details` (Настройки — name/email/password/notification toggles, one `name` field, no first/last split), `/logout`. `AccountTabs` (`src/components/site/account-tabs.tsx`) is the shared 6-tab bar with icons (`account-tab-icons.tsx`), including default/hover/active states pulled from Figma's own component-states section — check that section for any element with interactive states before building one from scratch. `SubscriptionStatusBar` is shared too; its "Управление на абонамент" Stripe Portal link only shows when the subscription is **not** active — while active, payment method and shipping are managed on our own pages, the Portal is the recovery path for when something needs fixing. Every server action that updates something shown on the same page it's submitted from must call `revalidatePath` after a successful write — Next.js does not refresh a Server Component's props on its own just because a Server Action nested under it returned new state, so the page will show stale data otherwise (real bug, hit twice: `updateShipping` and `updateProfile`).
- There is no per-month "next drop date" to set. `Site.deliveryDay` (a number, default 21) is the one constant: the day of the month packages are delivered, admin-editable, unchanged until the owner changes it. Production runs on a fixed 4-week cycle counted back from that day — week 1: customers can choose/change their design; weeks 2-3: locked, production is running; week 4: delivery happens and the next drop is announced, so choosing reopens, but for the delivery *after* the one arriving that week (already final). `nextDeliveryDate()`, `dropMonth()` and `isDropLocked()` in `src/lib/stripe-sync.ts` all derive from `deliveryDay` — the next physical delivery date, which month a customer's pick right now attaches to (`dropMonth`, via the internal `pickTargetDate` — skips ahead one cycle during week 4), and whether picking is locked (`isDropLocked`: true only in weeks 2-3, `PICK_LOCK_LEAD_DAYS`=21 to `PICK_REOPEN_LEAD_DAYS`=6 days out). Do not reintroduce a stored per-month date; compute it.
- `src/app/(payload)/` is Payload's admin UI at `/admin` and its REST API at `/api/*`. These files are generated by Payload; do not edit them. `custom.css` there is the one place for admin styling.
- `src/app/(admin-tools)/` is staff-only pages that don't belong inside Payload's generated admin — currently just `/admin-tools/deliveries` (see "Delivery tracking" below). Own root layout, no brand fonts or site chrome, protected per-page via `getAdminUser()` (`src/lib/admin-auth.ts`), the same pattern `(account)` uses for customers.
- `src/blocks/index.ts` defines the section blocks an editor can put on a page (hero, fabric, usps, reviews, faq, cta, social, aboutStory, aboutWhen). They hold copy and images only. `src/components/blocks/` has the matching React component for each block, with the pixel layout. `render-blocks.tsx` maps one to the other. To add a section: add a block, add a component, add a case in render-blocks, run generate:types and a migration.
- `src/collections/Customers.ts` is the customer accounts collection (site login, separate from `users` which is the /admin login). Email verification and password reset are built into Payload; the Bulgarian email templates live in that file. `address` is populated automatically by Stripe at checkout and not shown to the customer; `shipping` (recipient name, postcode, carrier, one combined address-or-courier-office field) is the simpler model the customer actually edits, on `/account/address` — the two are intentionally separate, don't merge them. `src/lib/auth.ts` reads the signed-in customer and sets the session cookie: its own `tdrop-account-token`, not Payload's own cookie, and not read back through Payload's cookie-matching (`getCustomer()` hands the token to `payload.auth()` as an `Authorization: JWT ...` header instead) — Payload names its auth cookie `${cookiePrefix}-token` with no per-collection distinction, so without this the `users` (admin) and `customers` logins would silently overwrite the same browser cookie. `cookiePrefix` in `payload.config.ts` is set to `tdrop-admin` so the /admin login gets its own `tdrop-admin-token` instead of Payload's unqualified default. `src/lib/actions/auth.ts` holds the server actions behind the login, registration, lost password, reset and profile forms. `src/components/forms/` holds those forms.
- Account routes: `/register` and `/your-profile` are login forms (as on the old site), `/your-profile/register` signs up, `/your-profile/lost-password` and `/your-profile/reset-password` handle passwords, `/your-profile/verify` is the email link target, `/account` is the dashboard (redirects to `/your-profile` when signed out; lives in `src/app/(account)/`, not `(site)`), `/account/details` edits the profile, `/logout` signs out.
- Subscription data: `src/collections/Plans.ts` (what can be bought, with the Stripe price id), `Subscriptions.ts` (one row per Stripe subscription, `size`/`gender` here are just the original checkout defaults), `Payments.ts` (one row per invoice), `Categories.ts` (the drop themes, tick "active" for this month) and `CategorySelections.ts` (a customer's pick per month — design, size and gender together, unique per customer and month; a new pick edits all three at once, there's no separate "just change size" flow). Access rules are in `src/lib/access.ts`: admins write, customers read only their own rows.
- `/join` (full redesign 2026-09-16, `join-picker.tsx`) is a two-step funnel: pick gender/size/design, then "Избери" goes to `/join/delivery` (gender/size/theme carried as query params, no cart/session needed) which collects the same shipping fields as `/account/address` — courier office pickup is common in Bulgaria and Stripe's own address collection can't ask for it. Its "Поръчай" is what calls `startCheckout`.
- Stripe: `src/lib/stripe.ts` (client), `src/lib/actions/checkout.ts` (`startCheckout`, called from `/join/delivery`, creates a hosted Checkout Session in subscription mode; gender/size/theme/shipping all ride along as session metadata, read back out in `stripe-sync.ts` once the webhook lands — Checkout itself no longer collects shipping address or phone, `/join/delivery` already has both), `src/app/(site)/webhooks/stripe/route.ts` (Stripe posts events here; the signature is checked, each event id is stored in `webhook-events` so retries do nothing twice) and `src/lib/stripe-sync.ts` (turns Stripe sessions, subscriptions and invoices into our rows). A signed-out visitor also gets an account created right there on `/join/delivery` (email/password/password2 fields, same rules as `/register`) and is logged in immediately, before Stripe is even called, with that email attached to the Stripe Customer so Checkout shows it pre-filled — added 2026-09-16 after a live test showed the alternative (the webhook's own guest-checkout fallback in `resolveCustomer`, which emails a "choose your password" link) is a dead end whenever `RESEND_API_KEY` isn't set, since that email just prints to server logs instead of sending (see "Run it" above). That webhook fallback still exists and still fires for identities Stripe creates outside this flow (e.g. a subscription event that reaches us before the checkout session does), so it wasn't removed, just no longer the primary path. `/account/portal` sends a customer to the Stripe Customer Portal for invoices and cancelling. `/account/payment` is the one exception to "never build card forms": it embeds Stripe Elements' Payment Element directly (`src/components/forms/payment-method-form.tsx`, `@stripe/stripe-js` + `@stripe/react-stripe-js`) via a server-created SetupIntent (`src/lib/actions/payment.ts`) — card data still never touches our server, it's Stripe's own iframe, just not a separate Stripe-hosted page. Needs `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` in `.env.local` (from the same Stripe dashboard as `STRIPE_SECRET_KEY`) or the page shows "Плащанията още не са включени." instead of the form. Do not add a second card form anywhere else in the app; this one page is the sanctioned exception, not a precedent.
- Newsletter: `src/collections/Subscribers.ts` (double opt-in: pending until the emailed link is opened), `src/lib/actions/newsletter.ts` (the footer form), `src/app/(site)/newsletter/` (confirm and unsubscribe links plus their result pages). Put `/newsletter/unsubscribe?token=<token>` at the bottom of every mailing.
- `src/globals/Site.ts` is the site-wide settings global: announcement strip, nav, footer links, newsletter labels, socials, next drop date.
- `src/lib/payload.ts` fetches pages and the Site global for rendering. `src/lib/revalidate.ts` holds the hooks that refresh a page when it is saved in /admin.
- `src/payload.config.ts` is the CMS config: which collections exist, the database adapter, the rich text editor. `src/collections/` holds one file per collection. `src/payload-types.ts` is generated; run `npm run generate:types` after changing a collection.
- `src/migrations/` holds the database migrations. After changing a collection, run `npm run migrate:create -- <name>` then `npm run migrate`. Migrations are committed and run against Supabase on deploy. Drizzle push is off on purpose.
- `scripts/` holds one-off scripts run with `npm run payload run <file>`. `seed-admin.ts` creates the local admin user.
- `src/components/site/` holds the header, footer and shared bits (buttons, badges, the shirt image, social icons).
- `src/components/ui/` is shadcn. Add more with `npx shadcn@latest add <name>`.
- `src/app/globals.css` defines the design tokens. Colors start with `t-` (`bg-t-red`, `text-t-neon`). Fonts are `font-headline` (Dela Gothic One), `font-body` (Handjet), `font-dot` (Handjet too, as of 2026-09-16 — was DotGothic16, kept as a separate token in case it diverges again), `font-roboto`.
- `public/wp/` holds every image from the WordPress uploads folder, same paths minus `wp-content/uploads`.
- `reference/tokens.md` lists the colors, type sizes and page map pulled from the Elementor kit. `reference/screenshots/` has the WordPress renders each page is compared against.

## Rules for edits

- Copy stays in Bulgarian exactly as on the old site until the owner changes it.
- Milestone v0.2 wires the site up: Payload CMS for content and admin, Supabase Postgres, Stripe hosted Checkout. Forms still post to `#` until each task lands.
- Do not set `serverURL` in `payload.config.ts`. It makes media URLs absolute and `next/image` then refuses them. Email links use `NEXT_PUBLIC_SERVER_URL` directly.
- `package.json` has `"type": "module"`. Payload's CLI needs it. Config files use `.mjs` or `.ts`.
- Never commit `.env.local`. `.env.example` lists every variable with a comment.
- Next.js 16 differs from older versions. Read `node_modules/next/dist/docs/` before touching routing, fonts or metadata.
- Widths and offsets in the pages are copied from Elementor pixel values on purpose. Change them only when a screenshot comparison says so.
- Home and About render from Payload (pages `home` and `about`). If a page is missing in the database the route 404s; run `npm run seed:content` to load the copy. The other pages are still hard-coded JSX until their tasks land.
- Text fields render line breaks as `<br>` through the `Lines` helper, so an editor can break a heading by pressing Enter.

## Tests

```bash
createdb tdrop_test                                   # once
DATABASE_URI=postgres://localhost:5432/tdrop_test npm run migrate   # once, and after each new migration
npm test                                              # Vitest: Stripe sync and access rules, against tdrop_test
DATABASE_URI=postgres://localhost:5432/tdrop_test S3_BUCKET= npm run seed:content
npm run test:e2e                                      # Playwright: sign-up, login, drop pick, newsletter, on port 3111
```

- `tests/unit/stripe-sync.test.ts` feeds hand-built Stripe events (`tests/unit/fixtures/stripe.ts`) through `handleStripeEvent` and checks the rows. Add a fixture for every new event shape you meet in the sandbox.
- `tests/unit/stripe-sandbox.test.ts` replays `tests/unit/fixtures/sandbox/lifecycle-events.json`, real events recorded from the sandbox with test clocks (first invoice, renewal, failed card, cancel), in order and two at once. To record new ones, run the scenario against a listener and save the events list trimmed to the fields the sync reads.
- `tests/unit/access.test.ts` calls the Local API with `overrideAccess: false` as anonymous and as a customer. Every new collection needs a line there.
- The unit tests empty the tables, so run the seed after them before the browser tests.
- `.github/workflows/ci.yml` runs lint, typecheck, both suites and the build on every push to main and every pull request, against a Postgres service.

## Security rules

- Every collection and global sets `access` for every operation. Payload's default is "any logged-in user", and customers are logged-in users, so a missing rule lets a customer write admin data. Use the helpers in `src/lib/access.ts`.
- Server actions use the Local API, which skips those rules. Check `getCustomer()` inside the action and only write the signed-in customer's own rows.
- Public forms go through `rateLimited()` in `src/lib/rate-limit.ts`. It is per server instance; Payload's `maxLoginAttempts` on customers is the real lock.
- Headers come from `next.config.ts`. There is no strict Content-Security-Policy yet.

## Stripe setup

State on 2026-09-12: the sandbox has the product, the monthly 17.99 EUR price (already on the plan in /admin) and a default Customer Portal configuration. The webhook is order-independent: if an invoice or subscription event arrives before the checkout session, the customer is created from the Stripe record.

1. In the Stripe dashboard (sandbox until the owner picks the live account) create a product with a recurring monthly EUR price. Copy the `price_...` id into the plan in /admin > Планове.
2. Put the secret key in `.env.local` as `STRIPE_SECRET_KEY`, and the publishable key (same Developers > API keys page, starts `pk_...`) as `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` — this second one powers the embedded card form on `/account/payment`; without it that page shows "Плащанията още не са включени." instead of crashing.
3. Add a webhook endpoint for `https://<site>/webhooks/stripe` with the events `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`, `charge.refunded`. Copy its signing secret into `STRIPE_WEBHOOK_SECRET`.
4. Locally, run `stripe listen --forward-to localhost:3100/webhooks/stripe` and use the secret it prints.
5. Enable the Customer Portal in Stripe settings (Billing > Customer portal) and allow cancelling.

## Google/Facebook login for customers

Customer-only — never wired to `users`/`/admin`, which stays plain email+password. `src/lib/oauth.ts` holds the provider configs; `src/app/(site)/your-profile/oauth/[provider]/route.ts` starts the flow (CSRF `state` in a short-lived cookie), `.../[provider]/callback/route.ts` finishes it. Payload's `login()` needs a password and OAuth never gives us one, so the callback sets a fresh random password only the server ever sees and immediately logs in with it via the normal Local API (`payload.update` + `payload.login`) — reusing Payload's own stable auth path instead of hand-signing a JWT. Safe to repeat every OAuth login; any previous random password is just replaced, so a customer who originally set a real password loses it once they link an OAuth login (expected — they'd use "lost password" to set a new one). The buttons (`OAuthButtons`, in the three login/register forms) are hidden per-provider until both env vars below are set for it — nothing to toggle in code.

To turn a provider on:
- **Google**: [Google Cloud Console](https://console.cloud.google.com/) → APIs & Services → OAuth consent screen (External, fill in app name + support email) → Credentials → Create Credentials → OAuth client ID → Application type "Web application" → Authorized redirect URIs: add `<NEXT_PUBLIC_SERVER_URL>/your-profile/oauth/google/callback` (locally `http://localhost:3000/your-profile/oauth/google/callback`). Copy the Client ID and Client Secret into `.env.local` as `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.
- **Facebook**: [Meta for Developers](https://developers.facebook.com/apps/) → Create App (type "Consumer") → add the "Facebook Login" product → Facebook Login → Settings → Valid OAuth Redirect URIs: add `<NEXT_PUBLIC_SERVER_URL>/your-profile/oauth/facebook/callback`. App Settings → Basic: copy the App ID and App Secret into `.env.local` as `FACEBOOK_CLIENT_ID` / `FACEBOOK_CLIENT_SECRET`. A new Facebook app starts in Development mode, where only the app's own registered testers/admins can log in — real customers need the app switched to Live (Settings → Basic → toggle at the top), which requires the `email` permission to pass App Review first.
- Production needs its own redirect URI added in both consoles once the real domain is live (Vercel env vars, not `.env.local`).

## Delivery tracking (factory export)

`CategorySelections.fulfillmentStatus` (Чака плащане / Подготовка / Изчаква / Доставено / Отказано, `src/lib/delivery-status.ts` is the single source of truth for the options — the collection field and every consumer import from it) — set it per row either in `/admin > Дропове > Избори за дроп`, or more usably at **`/admin-tools/deliveries`** (linked from the /admin sidebar, "📦 Доставки" — a plain Next.js page outside Payload's own generated admin, protected by `getAdminUser()` in `src/lib/admin-auth.ts`, which reads Payload's own admin cookie directly since — unlike customers — admin sessions were never rerouted around Payload's cookie matching). That page joins each month's picks with the customer's phone/shipping info and shows an inline status dropdown per row (`updateFulfillmentStatus` action, `src/lib/actions/deliveries.ts`) plus an "Export CSV" button (`.../deliveries/export/route.ts`, admin-only, UTF-8 BOM so Cyrillic opens correctly in Excel) for sending the month's run to the factory.

## Deploy (Vercel + Supabase)

State on 2026-09-13: deployed at https://t-drop-t-drop.vercel.app from the Vercel team `t-drop`, project `t-drop`, git-connected to `main`. Every push to `main` runs CI on GitHub and a production build on Vercel. Environment variables for Production and Preview are set; change them with `vercel env` or in the Vercel dashboard, never in code. The sandbox webhook endpoint points at that URL. Still to do: point t-drop.net at Vercel, create the first /admin user, add `RESEND_API_KEY`.

1. Supabase project in eu-central-1 (Frankfurt). In Project Settings > API, disable the Data API (REST) and GraphQL. Nothing in this app uses them.
2. Connection strings, two of them. The direct host (`db.<ref>.supabase.co`) is IPv6-only and unreachable from a Mac without IPv6, so both come from the Connect dialog's pooler tabs. On Vercel `DATABASE_URI` is the **Transaction pooler** string (port 6543): serverless instances come and go and the session pooler's 15-client cap fills up in seconds, which shows as "There was an error initializing Payload" on every dynamic route. `DATABASE_URI_SESSION` is the **Session pooler** string (port 5432) and only `payload migrate` uses it, because migrations need session mode. Locally, the session string alone in `DATABASE_URI` is fine.
3. Create a public bucket `media` in Supabase Storage, make S3 access keys in Storage settings, and fill the `S3_*` and `NEXT_PUBLIC_MEDIA_HOST` variables. Then run `npm run seed:content` once against production so images land in the bucket.
4. Vercel project on the `main` branch, Node 22, build command `npm run build` (it runs `payload migrate` first, then `next build`). Set every variable from `.env.example`.
5. After the first deploy, open `/admin`, create the first admin user, then set the Stripe price id on the plan.
