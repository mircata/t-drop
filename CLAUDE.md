# T-Drop, Next.js port

Monthly t-shirt subscription site for Bulgaria (t-drop.net). This repo replaces the WordPress site whose backup sits in `wordpress-site/t-drop.zip`.

## Run it

```bash
npm install
cp .env.example .env.local   # then fill in DATABASE_URI and PAYLOAD_SECRET
npm run migrate              # creates the tables
npm run seed:admin           # creates admin@t-drop.local / tdrop-local-admin for /admin
npm run dev
```

Node 22 LTS and npm (`.nvmrc` pins it). No Bun. The dev server picks a free port when 3000 is busy.

Emails (verification, password reset) print to the dev console unless `RESEND_API_KEY` is set. To finish a local registration, copy the token from the `customers` table and open `/your-profile/verify?token=...`.

Local database: PostgreSQL 17 from Homebrew (`brew services start postgresql@17`, then `createdb tdrop`). `DATABASE_URI=postgres://localhost:5432/tdrop` works with no password. Production points the same variable at Supabase Frankfurt.

## Where things live

- `src/app/(site)/` is the public site, one folder per page. `page.tsx` is the page, `layout.tsx` holds the fonts, header and footer. Routes match the old WordPress slugs: `/`, `/about`, `/join`, `/register`, `/your-profile`, `/my-account`, `/cart`, `/checkout`, `/payment-confirmation`, `/payment-failed`. The `(site)` folder name is not part of the URL.
- `src/app/(payload)/` is Payload's admin UI at `/admin` and its REST API at `/api/*`. These files are generated by Payload; do not edit them. `custom.css` there is the one place for admin styling.
- `src/blocks/index.ts` defines the section blocks an editor can put on a page (hero, fabric, usps, reviews, faq, cta, social, aboutStory, aboutWhen). They hold copy and images only. `src/components/blocks/` has the matching React component for each block, with the pixel layout. `render-blocks.tsx` maps one to the other. To add a section: add a block, add a component, add a case in render-blocks, run generate:types and a migration.
- `src/collections/Customers.ts` is the customer accounts collection (site login, separate from `users` which is the /admin login). Email verification and password reset are built into Payload; the Bulgarian email templates live in that file. `src/lib/auth.ts` reads the signed-in customer and sets the session cookie. `src/lib/actions/auth.ts` holds the server actions behind the login, registration, lost password, reset and profile forms. `src/components/forms/` holds those forms.
- Account routes: `/register` and `/your-profile` are login forms (as on the old site), `/your-profile/register` signs up, `/your-profile/lost-password` and `/your-profile/reset-password` handle passwords, `/your-profile/verify` is the email link target, `/my-account` is the dashboard (redirects to login when signed out), `/my-account/details` edits the profile, `/logout` signs out.
- Subscription data: `src/collections/Plans.ts` (what can be bought, with the Stripe price id), `Subscriptions.ts` (one row per Stripe subscription), `Payments.ts` (one row per invoice), `Categories.ts` (the drop themes, tick "active" for this month) and `CategorySelections.ts` (a customer's pick per month, unique per customer and month). Access rules are in `src/lib/access.ts`: admins write, customers read only their own rows.
- Stripe: `src/lib/stripe.ts` (client), `src/lib/actions/checkout.ts` (the "Поръчай" button on /join creates a hosted Checkout Session in subscription mode), `src/app/(site)/webhooks/stripe/route.ts` (Stripe posts events here; the signature is checked, each event id is stored in `webhook-events` so retries do nothing twice) and `src/lib/stripe-sync.ts` (turns Stripe sessions, subscriptions and invoices into our rows; a guest buyer gets an account and a "choose your password" email). `/my-account/portal` sends a customer to the Stripe Customer Portal for cards, invoices and cancelling. Never build card forms.
- Newsletter: `src/collections/Subscribers.ts` (double opt-in: pending until the emailed link is opened), `src/lib/actions/newsletter.ts` (the footer form), `src/app/(site)/newsletter/` (confirm and unsubscribe links plus their result pages). Put `/newsletter/unsubscribe?token=<token>` at the bottom of every mailing.
- `src/globals/Site.ts` is the site-wide settings global: announcement strip, nav, footer links, newsletter labels, socials, next drop date.
- `src/lib/payload.ts` fetches pages and the Site global for rendering. `src/lib/revalidate.ts` holds the hooks that refresh a page when it is saved in /admin.
- `src/payload.config.ts` is the CMS config: which collections exist, the database adapter, the rich text editor. `src/collections/` holds one file per collection. `src/payload-types.ts` is generated; run `npm run generate:types` after changing a collection.
- `src/migrations/` holds the database migrations. After changing a collection, run `npm run migrate:create -- <name>` then `npm run migrate`. Migrations are committed and run against Supabase on deploy. Drizzle push is off on purpose.
- `scripts/` holds one-off scripts run with `npm run payload run <file>`. `seed-admin.ts` creates the local admin user.
- `src/components/site/` holds the header, footer and shared bits (buttons, badges, the shirt image, social icons).
- `src/components/ui/` is shadcn. Add more with `npx shadcn@latest add <name>`.
- `src/app/globals.css` defines the design tokens. Colors start with `t-` (`bg-t-red`, `text-t-neon`). Fonts are `font-headline` (Dela Gothic One), `font-body` (Handjet), `font-dot` (DotGothic16), `font-roboto`.
- `public/wp/` holds every image from the WordPress uploads folder, same paths minus `wp-content/uploads`.
- `reference/tokens.md` lists the colors, type sizes and page map pulled from the Elementor kit. `reference/screenshots/` has the WordPress renders each page is compared against.

## Rules for edits

- Copy stays in Bulgarian exactly as on the old site until the owner changes it.
- Milestone v0.2 wires the site up: Payload CMS for content and admin, Supabase Postgres, Stripe hosted Checkout. Forms still post to `#` until each task lands.
- Do not set `serverURL` in `payload.config.ts`. It makes media URLs absolute and `next/image` then refuses them. Email links use `NEXT_PUBLIC_SERVER_URL` directly.
- `package.json` has `"type": "module"`. Payload's CLI needs it. Config files use `.mjs` or `.ts`.
- Never commit `.env.local`. `.env.example` lists every variable with a comment.
- Next.js 16 differs from older versions. Read `node_modules/next/dist/docs/` before touching routing, fonts or metadata.
- Widths and offsets in the pages are copied from Elementor pixel values on purpose. Change them only when a screenshot comparison says so.
- Home and About render from Payload (pages `home` and `about`). If a page is missing in the database the route 404s; run `npm run seed:content` to load the copy. The other pages are still hard-coded JSX until their tasks land.
- Text fields render line breaks as `<br>` through the `Lines` helper, so an editor can break a heading by pressing Enter.

## Security rules

- Every collection and global sets `access` for every operation. Payload's default is "any logged-in user", and customers are logged-in users, so a missing rule lets a customer write admin data. Use the helpers in `src/lib/access.ts`.
- Server actions use the Local API, which skips those rules. Check `getCustomer()` inside the action and only write the signed-in customer's own rows.
- Public forms go through `rateLimited()` in `src/lib/rate-limit.ts`. It is per server instance; Payload's `maxLoginAttempts` on customers is the real lock.
- Headers come from `next.config.ts`. There is no strict Content-Security-Policy yet.

## Stripe setup

State on 2026-09-12: the sandbox has the product, the monthly 17.99 EUR price (already on the plan in /admin) and a default Customer Portal configuration. The webhook is order-independent: if an invoice or subscription event arrives before the checkout session, the customer is created from the Stripe record.

1. In the Stripe dashboard (sandbox until the owner picks the live account) create a product with a recurring monthly EUR price. Copy the `price_...` id into the plan in /admin > Планове.
2. Put the secret key in `.env.local` as `STRIPE_SECRET_KEY`.
3. Add a webhook endpoint for `https://<site>/webhooks/stripe` with the events `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, `customer.subscription.deleted`, `invoice.paid`, `invoice.payment_failed`. Copy its signing secret into `STRIPE_WEBHOOK_SECRET`.
4. Locally, run `stripe listen --forward-to localhost:3100/webhooks/stripe` and use the secret it prints.
5. Enable the Customer Portal in Stripe settings (Billing > Customer portal) and allow cancelling.

## Deploy (Vercel + Supabase)

1. Supabase project in eu-central-1 (Frankfurt). In Project Settings > API, disable the Data API (REST) and GraphQL. Nothing in this app uses them.
2. Connection string: the direct host (`db.<ref>.supabase.co`) has only an IPv6 address, so from a Mac without IPv6 it cannot be reached. Use the **Session pooler** string from the Connect dialog (port 5432, user `postgres.<ref>`) both locally and on Vercel; it works for migrations and runtime. Never the Transaction pooler (port 6543), Payload's migrations need session mode. Put it in Vercel as `DATABASE_URI`.
3. Create a public bucket `media` in Supabase Storage, make S3 access keys in Storage settings, and fill the `S3_*` and `NEXT_PUBLIC_MEDIA_HOST` variables. Then run `npm run seed:content` once against production so images land in the bucket.
4. Vercel project on the `main` branch, Node 22, build command `npm run build` (it runs `payload migrate` first, then `next build`). Set every variable from `.env.example`.
5. After the first deploy, open `/admin`, create the first admin user, then set the Stripe price id on the plan.
